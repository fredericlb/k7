# One deploy key, owned by pl8

A studio user has **one** SSH deploy key, generated by pl8, and pastes its public half into their
git host once. They see it in the Sync tab of `/@settings`
(`apps/st0/frontend/src/settings/SyncSection.tsx`) — the one tab the hosted studio draws even
though the other three need the desktop app, since the key is the account's and pl8 answers for
it either way.

pl8 generates it because pl8 is the service that **lists** repositories, and reading a repository
needs the key. Generating it on the engine's machine instead would be safer — the private half
would never travel — but it leaves the one service that has to read a repository unable to.

The alternative is a second key — pl8 reads with one, the engine machine clones with another, and
you register both. It keeps every private half where it is made, and it is rejected because two
deploy keys to add, per user, per git host, is a setup step people get wrong, and the failure
mode ("pl8 can see the repo but st0 cannot clone it") is confusing in a way a single key never
is.

## So the private key travels

pl8 serves it to the file service over the channel those two **already** have: `MEDIATEK_URL` +
`MEDIATEK_TOKEN`, the bearer the supervisor gives the file service so it can sync the médiathèque
cache (`packages/file-service/src/mediatekPull.ts:58`). No new transport, no new credential. The
receiving side is `packages/file-service/src/sshKeys.ts`, which asks only when this machine has
no key of its own.

What guards it:

- the route is **bearer only** — a session cookie is not accepted, so no page in any browser can
  ever be navigated into fetching it, and no CSRF shape applies;
- **who** the key belongs to is settled per token KIND, not assumed. An account token answers for
  itself and may name nobody else; a service token — which is what a machine actually holds — has
  to name the person, and any name it gives is honoured. That last part is a real cost, taken
  deliberately: see the next section and `apps/pl8/docs/sshKeyForService.md`;
- `Cache-Control: no-store`, and the value is never logged on either side;
- in production the hop is HTTPS. In dev both processes are on one machine and it is
  `http://localhost:8795`.

What is accepted: a hosted service holds a credential that reaches your git host, and a copy
lands on every machine you run an engine on. Revoking is one action — delete the key at the git
host, then `POST /api/projects/ssh-key` for a fresh one — but it is an action you have to take,
and the old copies stay on disk until they are overwritten.

## The token a machine actually holds

A machine's token is minted by `scripts/tokens.mjs` with `sub: "service:st0"` — a **service**
identity, pinned by `packages/engine-host/src/tokensScript.test.ts`. A service identity has no
key of its own: treating the token's subject as the owner answers `404 no SSH key yet` while the
person's key exists, and sends you regenerating one that is already there.

Hence the rule: **the route accepts a service token that NAMES the person** (`?user=…`). One
value to manage per machine, and the accepted price is that the bearer of that token can ask for
anybody's key. The other way out — an ACCOUNT token per machine, which `POST /api/token` already
knows how to mint — needs a UI to paste it into that does not exist, and breaks the test above.

The detail (the email → subject bridge, what stays refused, what checks it) is in
`apps/pl8/docs/sshKeyForService.md`. The machine must also know **where** to ask:
`packages/file-service/docs/mediatekLink.md`.

## A machine that already holds one keeps it

`ensureKey` fetches **only when there is no private key on disk**. A machine that already has one
at that path — generated locally and registered at the git host — keeps it: nothing is fetched,
and clones, commits and pulls all keep using the key that works.

The consequence to know: that machine and pl8 then hold *different* keys, and pl8 can only list a
repository the key **it** holds can read. Both are registered at the git host, so both work; but
if you ever wonder why deleting one key at the host breaks listing while cloning still works,
this is why. Deleting the local `<state>/ssh/<slug>/` makes the machine adopt pl8's key on the
next clone.

## Installing a received key

`installKey` writes the private half `0600` and, **on Windows, also breaks ACL inheritance**
(`icacls /inheritance:r /grant:r <user>:F`). This is not belt-and-braces: OpenSSH on Windows
judges a key by its ACL and ignores the mode entirely, so a key written with `mode: 0o600` alone
is refused with `UNPROTECTED PRIVATE KEY FILE` and the clone fails with a message about
permissions rather than about anything the user did.

`ssh-keygen` sets all of this itself, which is why the generating side does not need it and the
code that receives a key does.

The public half is written when it is sent, but it is not required: an OpenSSH-format private key
carries its own public half, so `ssh -i` works without a `.pub` beside it. It is written so that
`publicKey()` answers on the receiving side too.

## The URI vocabulary — `uri.ts`

**SSH only.** The per-user key above is what carries the privilege, so an https URI would
sidestep it entirely and then hang on a credential prompt. Two spellings are accepted,
`git@host:path` and `ssh://host/path`, and both patterns anchor on an alphanumeric first
character — a URI must never reach `git` looking like an option.

`normalizeGitUri` folds those two spellings into one comparison key, `host[:port]/path`, with no
`.git` and no SSH user, port 22 dropped, host lowercased. It matters because
`git@host:me/repo.git` and `ssh://git@host/me/repo` are the **same repository**, and the two
sides of this feature learn about it by different routes: pl8 from what a person pasted, the file
service from a checkout's `remote.origin.url`, which git may have rewritten. Comparing the raw
strings would clone a repository that is already there
(`apps/st0/frontend/docs/projects.md`).

It **throws** on anything `assertSshGitUri` refuses: a key derived from an unvalidated string
would be a key for something that must never be fetched.

`repoNameOfKey` exists as its own door because a normalized key is `host/path` and is *not an SSH
URI any more* — handing it back to `repoName` throws. That is correct of the validator: one that
accepted its own output would accept a bare hostname as a repository. Callers holding a
normalized origin — the file service reads one off every checkout — need this door instead.

## The ssh invocation

`sshCommand` builds the `GIT_SSH_COMMAND` every git subprocess runs with, and each option is
load-bearing:

| option | why |
|---|---|
| `-i <key>` | the key to offer |
| `IdentitiesOnly=yes` | stop a running agent offering the human's own keys instead |
| `BatchMode=yes` | fail rather than prompt — there is no terminal to answer |
| `StrictHostKeyChecking=accept-new` | pin the host key on first sight, into… |
| `UserKnownHostsFile=<dir>/known_hosts` | …**our** file, not the machine user's |

Paths are spelled with forward slashes because git splits this string sh-style even on Windows.

`gitEnv` adds the rest, and two of them are security rather than hygiene:
`GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` stop a personal `url.insteadOf` rewrite
from turning the SSH URI back into https — privilege and all — and `GIT_TERMINAL_PROMPT=0` makes
a missing credential an error instead of a hang.
