# One deploy key, owned by pl8

A studio user has **one** SSH deploy key, generated by pl8, and pastes its public half into
their git host once.

That is a change. The key used to be generated by the file service, on the engine's machine,
and the private half never left it (`packages/file-service/src/sshKeys.ts`, before this).
That was the safer arrangement and it stopped working the moment pl8 became the service that
lists repositories: reading a repository needs the key too, and pl8 is not on that machine.

The alternative was a second key — pl8 reads with one, the engine machine clones with another,
and you register both. It keeps every private half where it is made. It was rejected because
two deploy keys to add, per user, per git host, is a setup step people get wrong, and the
failure mode ("pl8 can see the repo but st0 cannot clone it") is confusing in a way a single
key never is.

## So the private key travels

pl8 generates it and serves it to the file service over the channel those two **already**
have: `MEDIATEK_URL` + `MEDIATEK_TOKEN`, the bearer the supervisor gives the file service so
it can sync the médiathèque cache (`packages/file-service/src/mediatekPull.ts:58`). No new
transport, no new credential.

What guards it:

- the route is **bearer only** — a session cookie is not accepted, so no page in any browser
  can ever be navigated into fetching it, and no CSRF shape applies;
- **who** the key belongs to is settled per token KIND, not assumed. An account token answers
  for itself and may name nobody else; a service token — which is what a machine actually
  holds — has to name the person, and any name it gives is honoured. That last part is a real
  cost, taken deliberately: see « Le token que la machine a vraiment » below and
  `apps/pl8/docs/sshKeyForService.md`;
- `Cache-Control: no-store`, and the value is never logged on either side;
- in production the hop is HTTPS. In dev both processes are on one machine and it is
  `http://localhost:8795`.

What is accepted: a hosted service holds a credential that reaches your git host, and a copy
lands on every machine you run an engine on. Revoking is one action — delete the key at the
git host, then `POST /api/projects/ssh-key` for a fresh one — but it is an action you have to
take, and the old copies stay on disk until they are overwritten.

## Le token que la machine a vraiment

Ce qu'une machine détient est frappé par `scripts/tokens.mjs` avec `sub: "service:st0"` — une
identité de **service**, épinglée par `packages/engine-host/src/tokensScript.test.ts`. Une
identité de service n'a pas de clé à elle.

Cette page a d'abord décrit l'inverse (« le sujet EST le propriétaire »), et la fonctionnalité
ne pouvait donc marcher sur aucune machine : la route répondait `404 no SSH key yet` même
quand la clé de la personne existait, en envoyant en régénérer une déjà là.

Ce qui a été retenu : **la route accepte un token de service qui NOMME la personne**
(`?user=…`). Une seule valeur à gérer par machine, et le prix assumé est que le porteur de ce
token peut demander la clé de n'importe qui. L'autre sortie — un token de COMPTE par machine,
ce que `POST /api/token` sait déjà frapper — demandait une interface pour le coller qui
n'existe pas, et cassait le test ci-dessus.

Le détail (le pont email → sujet, ce qui reste refusé, ce qui le vérifie) est dans
`apps/pl8/docs/sshKeyForService.md`. Et pour que la requête parte seulement, il a fallu que la
machine sache **où** demander : `packages/file-service/docs/mediatekLink.md`.

## A machine that already had one keeps it

`ensureKey` fetches **only when there is no private key on disk**. A machine set up before
this change has one at the same path, generated locally and already registered at the git
host, so nothing is fetched and nothing breaks — clones, commits and pulls all keep using the
key that already works.

The consequence to know: that machine and pl8 then hold *different* keys, and pl8 can only
list a repository the key **it** holds can read. Both are registered at the git host in that
situation, so both work; but if you ever wonder why deleting one key at the host broke
listing while cloning still worked, this is why. Deleting the local `~/.studio/ssh/<slug>/`
makes the machine adopt pl8's key on the next clone.

## Installing a received key

`installKey` writes the private half `0600` and, **on Windows, also breaks ACL inheritance**
(`icacls /inheritance:r /grant:r <user>:F`). This is not belt-and-braces: OpenSSH on Windows
judges a key by its ACL and ignores the mode entirely, so a key written with `mode: 0o600`
alone is refused with `UNPROTECTED PRIVATE KEY FILE` and the clone fails with a message about
permissions rather than about anything the user did.

`ssh-keygen` sets all of this itself, which is why the generating side never needed it and
why the code that receives a key does.

The public half is written when it is sent, but it is not required: an OpenSSH-format private
key carries its own public half, so `ssh -i` works without a `.pub` beside it. It is written
so that `publicKey()` answers on the receiving side too.

## The ssh invocation

`sshCommand` builds the `GIT_SSH_COMMAND` every git subprocess runs with, and each option is
load-bearing:

| option | why |
|---|---|
| `-i <key>` | the key to offer |
| `IdentitiesOnly=yes` | stop a running agent offering the human's own keys instead |
| `BatchMode=yes` | fail rather than prompt — there is no terminal to answer |
| `StrictHostKeyChecking=accept-new` | pin the host key on first sight, into… |
| `UserKnownHostsFile=<dir>/known_hosts` | …**our** file, not the machine user's |

Paths are spelled with forward slashes because git splits this string sh-style even on
Windows.

`gitEnv` adds the rest, and two of them are security rather than hygiene:
`GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` stop a personal `url.insteadOf`
rewrite from turning the SSH URI back into https — privilege and all — and
`GIT_TERMINAL_PROMPT=0` makes a missing credential an error instead of a hang.
