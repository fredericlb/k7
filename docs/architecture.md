# Architecture — what each directory and package of the repo is

The reference map of the repo: read it before working in an area you do not know yet, or before
touching packaging and deployment. The root `AGENTS.md` keeps a one-line map and the rules every
task needs. A path written `docs/…` beside a package or an app means that zone's own `docs/`, as
everywhere in this repo ([lints.md](lints.md), which also holds the repo's own checks).

## The apps and the engine

`studio` holds the music/stage apps. The audio side spans the server and the musician's machine,
which is why this overview lives in the root `docs/` and not inside any one app. Two processes run on the
musician's machine — `engine/k7-runtime` and `engine/k7-supervisor` — either on their own, as the
command-line engine (`k7-supervisor --config <file>`), or inside an app: the tray (`apps/k7-tray`), through the k7 backend it runs, or the phone (`engine/k7-android`, `engine/k7-ios`). They also run on the server, as one more
machine in an image of their own (`docs/server-engine.md`):

| dir | language | what it is |
|---|---|---|
| `engine/k7-runtime` | C++ | The audio engine. Receives a compiled `ProjectDoc` over WebSocket, diffs it, plays audio, pushes transport and meter state back. **Never parses song files.** |
| `engine/k7-supervisor` | C++ | The engine machine's **supervisor**: starts, adopts and watches the engine, keeps it listed at the studios it is connected to, holds the tunnel a server reaches the machine through, and runs the work a server asks of the machine — a stem cut, a set list brought down, a file for the player (`docs/supervisor.md`). |
| `engine/scripts` | Node | The scripts that build the engine and the supervisor and package what ships: the command-line engine's archive, and the tray's release files around the same binaries (`engine/scripts/docs/buildEngine.md`). |
| `engine/k7-android` | Kotlin (Gradle) | The engine on a PHONE: the same engine as a library the app loads, since JUCE's Android audio reaches Java, and the same supervisor as a program it runs, driven over stdio as k7's backend drives it under the tray. STANDALONE like the tray: it also runs k7's backend, bundled, under Termux's node, so a phone opens its own studio and needs no server. Foreground only (`engine/k7-runtime/docs/android.md`). |
| `engine/k7-ios` | Swift (Xcode) | The same on an IPHONE, part for part, with what iOS forbids answered: no app may run a program or start a process, so the engine AND the supervisor are frameworks run on threads of the app, node is NodeMobile, the backend a worker thread of it, and each account's file service a worker thread of the backend. The shell page and the page scripts are Android's own. Staged by `scripts/stage.mjs` before Xcode builds it (`engine/k7-runtime/docs/ios.md`). |
| `apps/k7` | TypeScript | The text-first DAW, and the only app that opens a project: `frontend` (React/Vite) + `backend` (Express — the origin's OIDC flow, which MINTS the session every studio service verifies, the account's preferences, and the **media library** below; one process, `apps/k7/backend/src/server.ts`). Owns the timeline; shares the chains view. **Modules and chains are authored here**, against a project where the plugin a module names is actually LOADED, and written into one of the origin's libraries by an admin, who edits a library live from any project — a library is a plain folder on the server, seeded once from `k7-core/`, which every account reads at once (`packages/song/docs/sharedFolders.md`). A project is created from one of five **archetypes**: three named after the surface they open on — `arrangement` (a timeline), `mix` (two decks and a crossfade — `packages/song/docs/setProject.md`), `video` (a timeline and a viewport) — and the two `live` ones, named after what they ARE: a rig you play THROUGH, with nothing arranged and no lane of any kind — an input, a fader, the master run, and in `live-video` a webcam feeding RENDER plus the one viewport a picture cannot do without (`packages/song/docs/liveProject.md`) — and a song holds **sound and picture** alike: video lanes on the same timeline, whose ruler reads bars or seconds, and a `viewport` surface that composites them (`docs/picture.md`). What it draws beyond its panes, it draws because the project DECLARED it, in `surfaces/` (`docs/surfaces.md`). It opens the account's **playlists** as well — `_playlists/` at the workspace root, listing songs that live in the media library's catalogue, which this app searches and uploads into (`frontend/docs/playlists.md`). A `turntables` surface NAMES one, and that is what the DJ desk's browser lists and what the machine pre-fetches before a gig. Beside those, `_references/` — the finished mixes you listen AGAINST, uploaded there and played by the BROWSER so a reference sounds over a live rig or a running arrangement without going near the engine (`frontend/docs/references.md`). It owns the level above a project too: its **home page** — the ORIGIN with no project in the address — lists the account's workspaces, the projects inside them, the libraries and the published shares (`frontend/docs/projects.md`) — and its left sidebar carries the origin's USER MENU — the account, the other apps, the logout (`packages/ui-user-menu/docs/userMenu.md`). It is the **front door**: it answers the origin root, `app.k7.rocks` / `app.priv.k7.rocks` (the private instance), and `docs.k7.rocks` / `docs.priv.k7.rocks` with its documentation alone (`frontend/docs/docsSite.md`), and a project is addressed `/@local/<workspace>/<project>` — a folder on the machine that holds it, with `@banc` (the bench, a live rig seeded with a library chain) and `@shares` (a project at a checkpoint, played by the server's engine) the only other openable addresses — plus `/external`, the menu of surfaces a second device drives (`frontend/docs/external.md`). Opened ON one WORKSPACE otherwise, by an address rather than a picker — see `packages/project-shell/docs/launch.md`. A workspace is one folder holding SEVERAL projects: the editor's tree is the whole of it and a ▶ on a project row is what hands that one to the engine (`packages/file-service/docs/activeProject.md`). It is no git repository: it lives on the server and reaches every device through the live-sync relay, which is also where its history will come from (`docs/live-sync-plan.md`). |
| `apps/k7` — the médiathèque | TypeScript | The **media library** — songs, samples, recordings — is k7's too: its routes are mounted inside k7's backend (`apps/k7/backend/src/media/`, `mountMedia`) over a volume of files, and its screens are `@studio/ui-library`, mounted under `/media` with its sections as entries of the home sidebar. It holds **no modules and no chains**: those are authored in the editor, for the reason above. It DOES hold **playlists**, under `playlists/` on the volume and with a section of their own — a root zone rather than a family, since a set list names songs and carries no bytes (`packages/ui-library/docs/playlists.md`). A workspace keeps its own under `_playlists/`, in the same format and for a different job: those are versioned with the songs they were written for, and are the ones a `turntables` surface can name (`packages/song/docs/playlists.md`). The same backend holds the published shares (`/api/shares`), the engine registry (`@studio/engine-registry`), and — through `@studio/file-hub` — the accounts' WORKSPACES, one file service per account. `play.st0.app` is a permanent former host — installed supervisors and sent share links name it — answering `/api/*` and sending every page to `/media/…` at k7's origin (`packages/web-protocol/docs/addresses.md`); "pl8" survives only as the library's identifier (its engine session, its registry's endpoint file). |
| `apps/k7` — the rehearsal recorder | TypeScript | The **rehearsal recorder** — sessions and their takes, releases and the public pages that list them, singing exercises and a tuner — is k7's as well: its routes are `@studio/rehearsal-server`, mounted inside k7's backend BEFORE the media library (`mountRehearsal`), over a SQLite store of its own for the rows (`packages/rehearsal-server/docs/store.md`) and the media library for every recording's bytes (`packages/rehearsal-server/docs/audio.md`); its screens are `@studio/ui-rehearsal`, mounted under `/rehearsal` with a **Rehearsal** group in the home sidebar, and a take is held ABOVE the home's routes so it survives moving between pages (`packages/ui-rehearsal/docs/sections.md`). A public page, `/rehearsal/@<nametag>`, is read before the sign-in gate. `k7.st0.app` is a permanent former host — saved publish URLs and tokens, public page links and installed PWAs name it — answering `/api/*` and sending every page to `/rehearsal/…` at k7's origin (`packages/ui-rehearsal/docs/routing.md`); the publish feature (`project share k7`), the `K7_*` keys and the `k7-data` volume are the recorder's. |
| `apps/k7-tray` | Rust (Tauri) | **k7 on a computer**: a windowless Tauri app in the menu bar that starts one process, k7's backend bundle under a pinned node, on `http://127.0.0.1:18789` (the port in `apps/k7/backend/standalone.json`, the table the phone uses too). That backend runs the account file services and the machine's supervisor over stdio, on `~/.k7` and 8765, the same engine the command-line one would be (`apps/k7/backend/docs/localEngine.md`). The person opens k7 in their own browser at that address and can install it as an app; everything it needs is on the machine, so it works offline. The tray draws one status line the backend words and opens k7; it computes no policy. Released on its own by `.github/workflows/tray.yml` and kept current from `k7.rocks/app_downloads/tray` by tauri-plugin-updater (`apps/k7-tray/docs/tray.md`). A REMOTE engine is the hosted app's, reached through the relay or WebRTC, online only. |

## The shared packages

`packages/` is **studio's own shared tier**. All are `@studio/*` and are consumed
as **raw TypeScript source**: no build step, imported through `package.json`
`exports` subpaths, so a bare deep import fails on purpose.

| group | packages |

One of these is a **process rather than a library**, started rather than imported:
`file-service` (`bin: studio-file-service`), which `@studio/file-hub` runs from k7's backend, one
process per account.

They are named `@studio/*` rather than `@k7-core/*` because k7 is only one of
their consumers: apps in other repositories consume four of them. Those four — `web-protocol`,
`engine-protocol`, `engine-browser` and `project-shell` — are the only ones PUBLISHED, by version and
still as raw TypeScript (`docs/publishing.md`); every other package stays private to this tree.

## Production

**In production the hosted app is ONE image** (`docker/docker-compose.yml`): k7 (the
editor, the media library and the rehearsal recorder), built here, one Node process serving its own
built frontend with no nginx, reached at `app.k7.rocks`, at `docs.k7.rocks` for its documentation,
and on the former `st0.app` hosts that saved links still name. The rehearsal recorder's store is a
SQLite file on k7's `k7-data` volume, not a container. One session covers every host through the
shared `COOKIE_DOMAIN`. `engine/k7-runtime` and
`engine/k7-supervisor` are not in it: the server's own engine is a container of its own,
`k7-runtime`, built here from `engine/docker/Dockerfile`, which reaches k7 through the tunnel
like any musician's machine, plays into a null sink, and makes the renders k7's image has no
engine binary for (`docs/server-engine.md`). `apps/k7-tray`
and `engine/k7-android` run on the musician's devices only. `docs/versioning.md` is the page.

## `commons/` and `k7-core/`

`commons/` is a **git submodule** — the shared base, also used by the `phare`
monorepo. Editing something under `commons/` means committing in two places:

```bash
cd commons && git commit -am "…" && cd ..
git add commons && git commit -m "bump commons"
```

`push.recurseSubmodules=on-demand` is configured, so pushing the parent pushes
commons first. Never edit `commons/` for something only studio needs — put it in
`packages/` instead: that is the line between "shared with phare" and "shared
inside studio".

`k7-core/` is a plain folder of this repository: the `@k7-core` modules library, the SEED the server
copies a library folder from once and the tray and phone bundles carry a copy of. It is here so
a module and the code it relies on change together, in one commit. It is a PUBLISHED version: its
`library.k7x` says which, and **a change to its content raises that `version`** in the same commit —
a version already installed is never rewritten, so an unchanged number reaches no machine
(`docs/library-versions-plan.md`). Its binaries (IRs, amp models,
presets) are ordinary tracked files; a path in it stays short, since a Windows checkout refuses one
past 260 characters.
